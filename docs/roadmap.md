# 路线图（Roadmap）

> 平台的能力扩张按**五层**推进。每层的判据不是"能不能接"，而是"接了之后 Agent 的哪类任务从不可行变成可行"。

---

## 五层能力模型

| 层 | 能力 | 价值 | 状态 |
|----|------|------|------|
| **L1 数据** | 只读实时查询（天气/快递/行情/归属/核验） | Agent 能"知道世界现在什么样" | 🟢 主体已上线，按域补齐 |
| **L2 动作** | 写入型操作（发消息、建日程、提交工单） | Agent 能"改变世界" | 🟡 待做：出参统一先行 |
| **L3 SaaS 集成** | Notion / 飞书 / GitHub / 企业微信 / CRM | 配一次 OAuth，几十个工具全通 | 🔴 留存抓手，未启动 |
| **L4 AI 能力** | OCR / 翻译 / 语音 / 图像理解（非模型本体） | 补齐多模态输入输出 | 🔴 未启动 |
| **L5 自动化** | 定时任务、事件触发、编排 | 从"被调用"到"主动跑" | 🔴 未启动 |

**顺序是刻意的**：L1 是入口（零接入成本、立刻有用），L3 是留存（接进企业数据就不想走），L5 是天花板（Agent 常驻干活）。跳层会做出一个"什么都能干但什么都不稳"的平台。

## 近期（工程约束驱动，不是新功能）

这几项是**上线更多工具/动作类能力的前置条件**，不做就不许扩：

1. **真 failover + 上游健康探测** — 接第二个同类供应商之前必须完成。当前主源顺序已确定化，但故障自动切换还没有。
2. **出参统一（响应归一契约）** — 动作类工具（L2）之前必须完成。只读工具返回脏一点还能凑合，写入型操作返回格式不统一会直接导致 Agent 误判成功/失败。
3. **参数 schema 覆盖率 100%** — 消灭 `required=[]` 的裸 Capability，组合约束全部进 schema。
4. **Adapter 健康看板** — 按上游维度看成功率/延迟/退款率，让"该不该换供应商"变成有数据的决定。

## 中期

- **SDK / 客户端示例库**：Python / Node 直连 HTTP 的最小封装，给不想走 MCP 的自研 Agent。
- **工具集（Toolset）预设**：把"客服 Bot 常用 8 个工具"打包成一键勾选，替代人肉挑。
- **多语言文档**：英文 README + usage，MCP 生态读者不限于中文圈。
- **配额可视化**：Key 维度日/月调用趋势与剩余额度预警（Webhook 通知）。
- **私有化部署包**：三层 Adapter 里"自定义"那层的完整闭环，给要自带数据源的客户。

## 长期判断（可能不做）

- **公开 MCP Server 目录/榜单**：明确**不做**。那是 registry 生意，与"数据接入层"是两回事，会把平台拖进内容运营。
- **上游 API 转售（批发）**：合规与账期风险高，除非有明确大客户。
- **模型侧能力（推理、编排）**：不做。平台只当数据的搬运工。

## 变更口径

路线图不按季度承诺，按**触发条件**推进：

> 某层的前置工程约束完成 + 真实调用量证明需求存在 → 才开该层新功能。

因此本文档里的"未启动"不代表不重视，只代表还没有让它值得做的数据。
